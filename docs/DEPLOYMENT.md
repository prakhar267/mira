## Explicit release workflow

1. Review and merge source through the normal repository process. CI performs required checks, builds the Worker, runs local built-artifact smoke, then hashes the entire artifact. A normal push **does not deploy**.
2. CI seals `mira-release-manifest.json` containing source SHA, runtime, timestamps, file hashes/sizes and clean-source status. It refuses altered resource identity, missing migrations/KV, synthetic bindings/public-local origins, billing activation, credential files, symlinks or files outside the artifact. Only the narrowly named generated audit/smoke evidence is allowed untracked.
3. CI uploads `mira-worker-<40-character SHA>` and evidence. The repository owner must restore GitHub Actions access and supply scoped Cloudflare credentials in a reviewed/protected production environment. Check current access; don't assume a workflow file ran.
4. With explicit deployment authorization, dispatch **Mira explicit artifact promotion** using the successful main-branch CI run ID and exact SHA. It checks trusted run provenance **before** checkout/install, downloads that run's artifact, verifies every hash and deploys without rebuilding.
5. A mandatory read-only post-deploy smoke compares `/api/health.commitSha` to the promoted SHA, records Cloudflare `versionId`, and retains its output. A mismatch or failed smoke fails the release. No provider inference, account creation, real email or payment action runs automatically.
6. Separately approve a finite provider evaluation budget, test identities and human device sessions before claiming conversation availability/quality. Historical provider scripts predate the new consent/schema contract; don't run them blindly against production. Use the checked-in current Worker/browser suites for account lifecycle coverage until an authorized provider evaluation is reviewed.

The compiled SHA is set by Vite from CI's `GITHUB_SHA`; local builds say `unreleased`. The manifest and deployed version are related but not interchangeable. A local test of compiled bytes does not prove a successful public promotion. Neither staged Cloudflare deployment nor production rollback was performed in this implementation run.

## Failure, migration and recovery boundary

A failed post-deploy smoke is a release incident, not a success with a warning. Record SHA/version/request IDs, contain new admission if necessary, inspect content-free health/operator metrics, and choose a compatible forward fix or owner-approved rollback. Do not auto-retry deployment or purchase credits.

This release adds revisioned state, transcript tables, policy/suppression evidence and queued mail. Old application code can bypass those new guarantees even if it understands SQLite. Therefore **prefer a forward fix**. A rollback must first demonstrate schema, consent, transcript, token and deletion-suppression compatibility in isolation. Never roll back to KV-authoritative or archived prototype code. Never delete a Durable Object migration to make rollback compile.

Legacy records validate on read and require new policy confirmation. Invalid/oversized legacy records fail closed instead of being silently truncated. Follow [storage migration/recovery](STORAGE-RECOVERY.md); do not bypass schema checks. Daily same-object snapshots are not independent backups. A restored object must replay current deletion/privacy suppression before serving any account data.
