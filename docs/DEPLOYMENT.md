Use official Node24.18.0 binaries / pnpm11.19.0 and the lockfile. Avatar
generation/checks pin the bundled zlib 1.3.1-e00f703 as well; Homebrew's
system-zlib build produces different valid gzip bytes and is refused by that

```sh
pnpm install --frozen-lockfile
pnpm db:generate
pnpm lint

pnpm test
pnpm --filter @companion/web test:worker
pnpm --filter @companion/web exec playwright install chromium firefox webkit
pnpm --filter @companion/web test:browser
pnpm --filter @companion/web build:vinext
node apps/web/scripts/artifact-smoke.mjs
```

The browser suite first builds the actual artifact, then runs it locally with synthetic HTTP/media fixtures on loopback4397; the built-artifact smoke uses4398 and refuses readiness from an unrelated process. Both execute the compiled modules/assets through the locked Miniflare/workerd runtime and Wrangler SDK configuration conversion, with unique local persistence and isolated credentials. A streaming loopback adapter uses `dispatchFetch` to avoid the reproduced Wrangler Dev ProxyWorker timing fault; it does not rebundle or replace application routes. See [runtime diagnosis and regression](READINESS-RECOVERY-PREPARATION.md#isolated-five-second-proxy-regression).

**`--local` alone does not disable Workers AI.** Both helpers enforce the runtime-only `MIRA_INFERENCE_DISABLED:true` override, block runtime outbound fetches, ignore source secret files and use a non-credential instead of owner OAuth. Readiness includes the inference-refusal probe. The sealed production config/bytes are not rewritten. Each of three smoke cold starts also exercises rejected request bodies and six send-time-aligned asset-integrity requests. HTTP checks cover rendered routes, headers, storage health, exact commit correlation and actual avatar bytes. They **do not** cover real providers, microphone acoustics or deployed Cloudflare networking. The HTTP-mocked browser specs block service workers because they otherwise bypass route fixtures; service-worker behavior is not certified by those specs. Synthetic storage remains in the reported temporary directory for inspection; no user directories are cleaned.

## Explicit release workflow

1. Review and merge source through the normal repository process. CI performs required checks, builds the Worker, runs local built-artifact smoke, then hashes the entire artifact. A normal push **does not deploy**.
2. CI seals `mira-release-manifest.json` containing source SHA, runtime, timestamps, file hashes/sizes and clean-source status. It refuses altered resource identity, missing migrations/KV, synthetic bindings/public-local origins, billing activation, credential files, symlinks or files outside the artifact. Only the narrowly named generated audit/smoke evidence is allowed untracked.
3. CI uploads `mira-worker-<40-character SHA>` and evidence, downloads it into a fresh directory and verifies the upload round trip. The public repository's Actions execution is verified. Automated promotion still requires scoped Cloudflare credentials in a reviewed/protected production environment; none were configured at the latest check. An explicitly authorized owner-CLI promotion may use the same provenance/hash checks without copying personal OAuth credentials into GitHub.
4. With explicit deployment authorization, dispatch **Mira explicit artifact promotion** using the successful main-branch CI run ID and exact SHA. It checks trusted run provenance **before** checkout/install, downloads that run's artifact, verifies every hash and deploys without rebuilding.
5. A mandatory read-only post-deploy smoke compares `/api/health.commitSha` to the promoted SHA, records Cloudflare `versionId`, and retains its output. A mismatch or failed smoke fails the release. No provider inference, account creation, real email or payment action runs automatically.
6. Separately approve a finite provider evaluation budget, synthetic test identities and human device sessions before claiming conversation availability/quality. The consent-aware evaluator below can prepare that check, but it is opt-in and not run automatically. Other historical provider scripts may predate current consent/schema contracts; do not run them blindly against production. Use the current Worker/browser suites for isolated account lifecycle coverage.

The compiled SHA is set by Vite from CI's `GITHUB_SHA`; local builds say `unreleased`. The manifest and deployed version are related but not interchangeable. A local test of compiled bytes does not prove a successful public promotion. [The September 14 release](READINESS-STATUS.md) verifies an exact-artifact production deployment; a real production rollback is not claimed. Later test/documentation-only commits need not redeploy an unchanged application, and must not be mislabeled as the live source SHA.

## Explicitly authorized conversation evaluation

`apps/web/scripts/conversation-eval.mjs` reads only the checked-in synthetic dataset. It has **no default live URL, authorization, consent or request budget**. Missing/invalid options and unknown scenario IDs fail before any network access. HTTPS is required except for HTTP loopback fixtures. Redirects, URL credentials/path/query/fragment and malformed cookies are refused. Use Node24.18.0.

Only after the owner approves the target, available provider allowance and finite test scope, an example four-turn subset is:

```sh
COMPANARO_URL=https://approved-mira-origin.example \
MIRA_EVAL_ALLOW_PROVIDER_REQUESTS=true \
MIRA_EVAL_MAX_REQUESTS=4 \
MIRA_EVAL_POLICY_VERSION=2026-09-13 \
MIRA_EVAL_ADULT_DECLARED=true \
MIRA_EVAL_AI_PROCESSING_CONSENT=true \
MIRA_EVAL_SCENARIOS=daily-smalltalk \
node apps/web/scripts/conversation-eval.mjs
```

Replace the example origin with the explicitly approved deployment; do not interpret the example as authorization to call production. The script creates one limited demo session through the real declaration contract, keeps its secure cookie in memory and attempts revocation on exit. It does not renew sessions to bypass the server's limits. The full dataset has 76 turns, while a demo principal allows at most 40 chat provider attempts; select an appropriate smaller subset. Model repair attempts can exhaust that allowance earlier.

`MIRA_EVAL_MAX_REQUESTS` caps attempted **chat HTTP requests**, including failures, not provider credits or individual upstream attempts. A single accepted request can use bounded server repair attempts. There are no client inference retries. Budget exhaustion, authentication/provider errors, invalid responses, failed demo revocation or a changed release produce an incomplete/failed report rather than a passing result. Server unit/daily/concurrency caps still apply. Health/session/revocation requests are separate from this chat cap.

An explicitly authorized, dedicated synthetic QA account may instead supply only its existing `__Host-companaro_session=<token>` through `MIRA_EVAL_ACCOUNT_COOKIE` in a securely managed environment. Never paste that token into a command history, GitHub, chat or evidence. Its current stored policy must already permit AI processing. The evaluator does not create, renew or revoke that account session. Do not use a real customer's account: canonical profile/memory settings can affect inference, even though input text comes from synthetic fixtures.

Reports go to a new temporary directory by default, or `QA_DIRECTORY` with exclusive file creation. They contain release IDs, scenario/turn IDs, hashes, heuristic flags, bounded metadata and latency summaries—not raw inputs, generated replies, cookies or raw service exceptions. A script/language/anchor pass is not a semantic-quality score; P50/P95/P99 are small-sample chat-HTTP observations, not end-to-audible voice latency. Fluent human review and the [physical call protocol](REAL-DEVICE-CALL-QA.md) remain separate. Routine regression tests inject local HTTP/mocks and consume no live provider allowance.

The evaluator now supports required **groups** of alternative fact anchors: a
question about a person and a city must match both groups, not either one. It
preserves explicitly selected scenario order (so the longest sequence can run
first), records per-language latency summaries and distinguishes bounded style,
safety and changed-context error codes. These are still review flags, not an
automatic semantic judge.

## Call-ready avatar delivery and repeatable slow-network lab

The default call profile is described in [the avatar licence and derivative
notice](../apps/web/public/assets/mira/avatar/LICENSE.md#call-ready-profile-default).
It preserves geometry/rig bytes but deliberately uses smaller, high-quality
textures. The original and pixel-identical derivative remain intact. Downloads
start alongside the lazy 3D code only after opening a video call; hang-up aborts
the owned request. A tiny portrait remains visible during loading. Both gzip
and raw-browser compatibility paths are size- and SHA-256-verified.

For a local Apple M4 comparison, after the browser build/check finishes:

```sh
pnpm --filter @companion/web build:vinext
node apps/web/scripts/avatar-metal-lab.mjs --slow-network
```

This explicitly macOS-only diagnostic starts isolated compiled Workers runtime
with blocked provider egress and synthetic media. It shapes the **call-opening**
phase to 1.6 Mbps down/0.8 Mbps up/150 ms latency, uses a cold mobile-emulated
393×851 viewport at DPR 1 with no CPU throttle, and requires the real Apple M4
Metal renderer. Each run writes new temporary JSON/screenshots and verifies
post-hang-up cleanup. Run three separate cold samples with no concurrent builds
for a comparison. Draw submissions/rAF are not presented FPS or lip-sync proof;
this is not a physical phone/acoustic or whole-page cold-start test. Do not run
Next and vinext builds concurrently: both manage generated `.next` route types.

## Failure, migration and recovery boundary

A failed post-deploy smoke is a release incident, not a success with a warning. Record SHA/version/request IDs, contain new admission if necessary, inspect content-free health/operator metrics, and choose a compatible forward fix or owner-approved rollback. Do not auto-retry deployment or purchase credits.

This release adds revisioned state, transcript tables, policy/suppression evidence and queued mail. Old application code can bypass those new guarantees even if it understands SQLite. Therefore **prefer a forward fix**. A rollback must first demonstrate schema, consent, transcript, token and deletion-suppression compatibility in isolation. Never roll back to KV-authoritative or archived prototype code. Never delete a Durable Object migration to make rollback compile.

Legacy records validate on read and require new policy confirmation. Invalid/oversized legacy records fail closed instead of being silently truncated. Follow [storage migration/recovery](STORAGE-RECOVERY.md); do not bypass schema checks. Daily same-object snapshots are not independent backups. A restored object must replay current deletion/privacy suppression before serving any account data.
